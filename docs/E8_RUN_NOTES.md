## 2. How to start the real run

Prerequisites: after 2026-10-09 05:00 UTC; `e2-issuer` stopped (the script refuses while it runs, while
`driver_oct9.sh` / `e2night/driver.sh` / `e2_night.py` runs, or before 05:00 UTC by the clock); `hpr-hass`,
`hpr-devices`, `hpr-broker` up; mains power. Write `exp/out/e8_preregistration.json` from the draft first.

```bash
cd <artifact-root>
mkdir -p <research-dir>/HOMEPROV-P13-exp/e8
nohup caffeinate -i -s testbed/e8/run_e8.sh e8_main > <research-dir>/HOMEPROV-P13-exp/e8/e8_main.out 2>&1 &
```

Preflight (refuses otherwise): the guards above; no leftover `homeprov_ec`/`homeprov_e7` in the hub; `python3 -m pytest
-q monitor` and `python3 -m pytest -q testbed/anchord` pass; both images build (monitor from `monitor/Dockerfile.sign`,
pinned `cryptography` 46.0.3, never the stock tags: the script refuses `:1`, `:sig`, `:linked`, `:e7` tags); the
in-image `monitor.py`, `anchord.py`, `anchord_linked.py` are byte-identical to the repository's; the images carry
signatures, reply tags, coverage, escrow, cost log, operator key and extension pushes; the monitor image imports
`cryptography`. It also refuses if the run directory, any `exp/out/e8_main_*` file, an `e8-*` container, volume or
network of the tag, or a witness port (19970, 19971) already exists.

What the run does to the default deployment, by design: stops and renames `hpr-monitor`/`hpr-anchord` for the run and
restores them on exit (gap in the default chain bounded by the run's window files); copies `homeprov_ec` and
`homeprov_e7` into the hub's `/config/custom_components` and lists one at a time in `configuration.yaml`; restarts
`hpr-hass` 2 times per configuration, once after the arms, twice in the stress phase; restores `configuration.yaml`
byte for byte (checked by sha256 at teardown); adds one container (`e8-e8_main-stress`) on the deployment network for
30 minutes. `hpr-devices` has no rate setting (`devices.py` reads only `HPR_BROKER` and `HPR_SEED`), so it is NOT
restarted or modified.

## 3. What runs

### 3.1 Monitors, anchors, witnesses, keys
- `e8-monitor-stb` (stable columns, the EVALUATED scheme) with `e8-anchord-stb`; `e8-monitor-clo` (closure, alongside)
  with `e8-anchord-clo`. Both monitors: `HOMEPROV_COVERAGE=1`, escrow (`<run dir>/escrow_{stb,clo}`), cost log,
  `HOMEPROV_SIGN_KEY=/sign/monitor.pem`, `HOMEPROV_REPLY_TAGS=1`, 5 s poll.
- Signing keys: one Ed25519 pair per monitor, generated by a one-shot container INSIDE that monitor's own volume
  (`e8-e8_main-{stb,clo}-sign`, mounted read-only by the monitor only); only the public key PEM leaves it
  (`<run dir>/keys/{stb,clo}_sign_pub.pem`, copied into `e8_main_score.json` with its fingerprint). The volumes, and
  with them the private keys, are destroyed at teardown.
- Anchors: the linked daemon (`anchord_linked.py` over `anchord.py`), link v2, a fresh append key, a SEPARATE fresh
  operator key (`HOMEPROV_OPERATOR_KEY`, hex), sync head pushes to a witness. Each anchor is on the deployment's internal
  network (alias `anchor-stb` / `anchor-clo`) and on a second, non-internal network (`e8-e8_main-wnet`) only so it can
  reach `host.docker.internal`.
- Witnesses: `headwitness.py` (run from a copy taken at start, hash logged) as two python3 processes on the Mac,
  127.0.0.1:19970 and :19971, each with its own fresh key and empty log, as in E5.
- Probes before the arms: from the hub, untagged / forged records and markers to both anchors, and the witness ports;
  from a throwaway container holding the keys in its environment, a marker under the append key, a record under the
  operator key, and one operator-key MIGRATE marker in `rig.marker_issuer`'s record format (inert:
  `rig.markers.explains()` excuses nothing for MIGRATE and `markers_from_chain()` keeps PURGE only), with every reply
  tag checked. Switch it off with `HPR_E8_OPERATOR_PROBE=0` if no marker is wanted on the evaluated chains.

### 3.2 Phase 1: arms (30 trials per configuration and arm, porch, hallway, kitchen: 90 per arm)
Per configuration: `homeprov_ec` with PU, PI, PSR, P (seal wait 130 s), then `homeprov_e7` with INS-L, INS-M (K = 9),
BD-S (forged row at least 130 s old, empty second searched over the last 1,800 s). No device pause is needed (BD-M is
not an E8 arm; empty seconds are plentiful). Reports: `exp/out/e8_main_report_ec_<room>.json`,
`exp/out/e8_main_report_e7_<room>.json`.

### 3.3 Phase 2: baseline and write-rate stress
90 s settle, a 600 s BASELINE window at the lab rate (no trials, no restarts), then a fixed 1,800 s STRESS window:
`stress_publisher.py` (image `hpr-devices:1`, the simulator's own image) drives the simulator's three motion topics
with the simulator's loop, every sleep divided by `HPR_E8_STRESS_FACTOR` (default 6); after a 300 s ramp the PU arm runs
30 trials in porch; the window ends at 1,800 s whatever the arm's length; the publisher sets every motion sensor OFF
on exit. Report: `exp/out/e8_main_stress_report_porch.json`.

Calibration on the scratch stack (recorder rows of states joined to states_meta plus events joined to event_types per
minute, 4-5 min windows; scratch, not results): baseline 32.0 / 34.6 / 35.0 rows per minute; factor 4: 125.8 (3.9x);
factor 6: 163.8 and 161.75 (about 4.7x); factor 7 with a 3-trial PU arm and one hub restart in the window: 199.02
(5.686x of that run's baseline); factor 25: 506.75. Factor 4 makes the motion EVENT rate five times the simulator's (the
simulator gives about 4 motion cycles per minute, the publisher at factor 4 about 16); factor 6 makes the WRITE rate
about five times the baseline once the PU arm's rows are in the window. **Decision for the lead:** "five times the lab
rate" relative to what. Default 6 targets five times this run's own baseline write rate. Relative to the pooled lab rate
in `r13_write_rate.json` (122.49 rows per minute, which includes trial rows and hub-restart bursts), factor 6 is only
about 1.3x; five times that (about 612 rows per minute) needs a factor near 30 (untested above 25).

### 3.4 Freeze and scoring
90 s settle; consistent recorder snapshot (SQLite backup API inside the hub; time in `<run dir>/snapshot_at`); 30 s; both
monitors stopped (the only appenders); 8 s (past the witness push timeout); witness heads and logs, chains, refusals,
published heads, cost logs, monitor and anchor logs, escrow. Then `exp/stages/e8_score.py`.

## 7. Risks and open points

1. **Stress target** (3.3): factor 6 means about five times this run's own baseline write rate, not five times the
   pooled r13 lab rate. Decide before writing the pre-registration.
2. **Code is still moving.** `monitor.py` changed during the dry runs (in-image `3e479ae0...` in dry run 1; the
   coordinator's e7_verify is `7e036386...`). The run builds from the files present at start, refuses if tests fail
   or the images differ from the repository, and records every hash; the pre-registration must pin the hashes the run
   will use. A short smoke on the real deployment is cheap: `HPR_E8_TRIALS=1 HPR_E8_ROOMS=porch HPR_E8_BASELINE_S=60
   HPR_E8_STRESS_S=300 HPR_E8_STRESS_RAMP_S=60 HPR_E8_STRESS_TRIALS=2 testbed/e8/run_e8.sh e8_smoke` (~25 min; writes
   `exp/out/e8_smoke_*`, to be moved out afterwards as E7 did).
3. **The operator probe puts one MIGRATE marker on each evaluated chain** (before `t_start`). It excuses nothing and
   e7_verify ignores markers; set `HPR_E8_OPERATOR_PROBE=0` to keep the chains marker-free.
4. **Witness placement**: on the same Mac as the Docker VM; outside the VM, not a separate party (stated in the draft's
   known limits). The anchors get a second, non-internal network to reach it; the hub does not (verified: the name
   does not resolve from the hub).
5. **Recovery render** (E7's escrow render of the closure monitor's restored copy) is kept behind
   `HPR_E8_RECOVERY_RENDER=1` (default 0, not in E8_DESIGN C) and was NOT exercised in these dry runs.
6. **Effects on the default deployment** (as E7): stock monitor and anchor down for the run (~3 h gap in the default
   chain, bounded by the window files); hub restarted 9 times; one extra publisher for 30 min. The scratch hub held a
   fresh recorder, so per-poll copy costs in the dry runs (median 4-13 ms) are far below what the 194 MB default
   recorder will show (E7 closure copy median 160 ms).
7. **E2 guard**: the E2 night's driver runs as `bash ./driver_oct9.sh` (relative path), which `run_e7.sh`'s pattern
   would have missed; `run_e8.sh` matches `driver_oct9.sh`, `e2night/driver.sh`, `e2_night.py`, and any `driver*.sh`
   whose working directory is under `e2night/`, plus a running `e2-issuer` container and the 05:00 UTC clock guard.
8. **PSR / BD-S misattribution fields** in the harness are not attack-success measures for those arms (above).
9. Power: ~3 h of sustained load; `caffeinate -i -s` is in the start command.
